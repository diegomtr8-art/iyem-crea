## 4. LOGIN / REGISTRO CON GOOGLE (OAuth)

### 4.1 Instalación

```bash
composer require laravel/socialite
```

### 4.2 Configuración

- Agregar a `config/services.php`:
  ```php
  'google' => [
      'client_id' => env('GOOGLE_CLIENT_ID'),
      'client_secret' => env('GOOGLE_CLIENT_SECRET'),
      'redirect' => env('GOOGLE_REDIRECT_URI'),
  ],
  ```
- Agregar a `.env.example` (sin valores reales):
  ```
  GOOGLE_CLIENT_ID=
  GOOGLE_CLIENT_SECRET=
  GOOGLE_REDIRECT_URI="${APP_URL}/auth/google/callback"
  ```
- NOTA: el usuario (Diego) proporcionará las credenciales reales de Google OAuth
  más adelante (Client ID / Secret desde Google Cloud Console). Dejar todo
  preparado para que solo falte configurar el `.env` de producción. Documentar en
  un comentario o en `CHANGELOG_AUDITORIA.md` qué URI de redirect debe registrarse
  en Google Cloud Console: `https://crea.iyemyucatan.com/auth/google/callback`

### 4.3 Migración — agregar columnas para OAuth

Crear migración para agregar a la tabla `users`:
- `google_id` (string, nullable, unique)
- `avatar` (string, nullable) — para guardar la foto de perfil de Google

### 4.4 Rutas

En `routes/auth.php`, dentro del grupo `guest`:
```php
Route::get('auth/google/redirect', [GoogleAuthController::class, 'redirect'])
    ->name('auth.google.redirect');
Route::get('auth/google/callback', [GoogleAuthController::class, 'callback'])
    ->name('auth.google.callback');
```

### 4.5 Controller

Crear `app/Http/Controllers/Auth/GoogleAuthController.php`:

- `redirect()`: `Socialite::driver('google')->redirect()`
- `callback()`:
  1. Obtener el usuario de Google (`Socialite::driver('google')->user()`)
  2. Buscar un `User` existente por `google_id` o por `email`
  3. **Si no existe ningún usuario con ese email**:
     - Crear un nuevo `User` con `tipo = 'ciudadano'`, `google_id`, `avatar`,
       `name`, `email`, `email_verified_at = now()` (Google ya verificó el
       correo), y una contraseña aleatoria hasheada (no usable, ya que entrará
       siempre por Google)
     - Asignar el rol correspondiente de Spatie si aplica (ver sección 5)
  4. **Si ya existe un usuario con ese email pero sin `google_id`**: vincular la
     cuenta (actualizar `google_id` y `avatar`) — esto permite que un ciudadano
     que ya se registró manualmente también pueda entrar con Google después
  5. **Si el usuario existente es de `tipo = 'operativo'`**: permitir el login con
     Google igualmente (vincular cuenta), respetando su tipo y permisos —
     SOLO los usuarios SIN cuenta previa que entran por primera vez vía Google se
     crean como `ciudadano`
  6. Iniciar sesión (`Auth::login($user)`)
  7. Redirigir según el tipo de usuario (ver sección 6 de routing)

### 4.6 Botón "Continuar con Google" (frontend)

Componente reutilizable `resources/js/components/GoogleLoginButton.vue`:
- Botón con el ícono oficial de Google (SVG multicolor — usar el SVG estándar de
  la "G" de Google, NO un emoji ni un ícono genérico)
- Texto: "Continuar con Google"
- Estilo: fondo blanco, borde gris claro, sombra sutil al hover, texto oscuro
  (sigue las guías de marca de Google: no recolorear el logo de Google)
- `<a :href="route('auth.google.redirect')">` (link normal, no fetch — debe hacer
  una navegación completa para el flujo OAuth)
- Usar este componente en `Login.vue` y `CiudadanoRegister.vue`

## 5. ROLES Y PERMISOS (Spatie Permission)

El usuario aún no tiene definidos todos los permisos, pero hay que dejar la base
lista y organizada:

### 5.1 Estructura de roles propuesta

Sin sobre-diseñar (el usuario ajustará después), crear/verificar en el seeder de
roles y permisos (`database/seeders/` — buscar si existe `RolesSeeder` o similar,
o crear `RoleAndPermissionSeeder`):

- **Rol `ciudadano`**: usuarios del portal `/mi-portal`. Sin permisos de Spatie
  especiales (controlado por middleware `EsCiudadano` + `tipo = 'ciudadano'`)
- **Roles operativos** (todos con `tipo = 'operativo'`, diferenciados por rol de
  Spatie y sus permisos):
  - `admin` / `super-admin`: todos los permisos, incluye gestión de usuarios y
    roles (`UserController`, `RoleController`)
  - `analista-credito`: permisos sobre `solicitudes.*`, `analisis.*`
  - `cajero` / `cobranza`: permisos sobre `pagos.*`, `cobranza.*`
  - `juridico`: permisos sobre `juridico.*`, `cobranza.juridico`
  - `consulta` / `lectura`: solo permisos de visualización (reportes, dashboard)

Definir los permisos como strings claros, agrupados por módulo, por ejemplo:
`solicitudes.ver`, `solicitudes.gestionar`, `pagos.registrar`, `pagos.cancelar`,
`cobranza.gestionar`, `juridico.ver`, `juridico.editar`, `reportes.ver`,
`usuarios.gestionar`, `roles.gestionar`, `presupuesto.gestionar`,
`auditoria.ver`, etc. — basarse en los controllers existentes en
`app/Http/Controllers/` para cubrir cada módulo operativo.

### 5.2 Aplicar permisos a las rutas

En `routes/web.php`, dentro del grupo `auth + verified + operativo`, agregar
middleware `can:` o `permission:` (Spatie) a las rutas sensibles según el mapeo
de permisos. NO romper rutas existentes — si un permiso aún no está bien definido,
dejar un comentario `// TODO: revisar permiso` en lugar de bloquear el acceso, ya
que el usuario terminará de definir la matriz de permisos después.

### 5.3 UI de gestión de roles

Revisar `resources/js/Pages/Roles/Index.vue` y `app/Http/Controllers/RoleController.php`
para confirmar que ya permiten crear roles y asignar permisos desde la interfaz
(checkboxes agrupados por módulo). Si la UI es básica, mejorarla visualmente
(agrupar permisos por módulo en acordeones o secciones, con el mismo estilo visual
del proyecto) pero sin cambiar la lógica de negocio si ya funciona.

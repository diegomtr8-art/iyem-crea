## CONTEXTO Y CÓMO USAR ESTE PROMPT

Abre primero `flujo_solicitud_y_formatos.html` en un navegador (o lee su código). Ese
archivo es la **especificación visual exacta** de lo que debe lograrse: muestra el
flujo completo (verificación CURP → modalidad/persona/garantía → formulario →
documentos → envío → revisión → aprobación → descarga de ZIP) y, lo más importante,
la **réplica visual de cada uno de los 5 PDFs oficiales ya llenados con datos de
ejemplo** (secciones 3 a 7 del HTML: F-PR-OCC-02, 03, 04, 05 y 07).

El objetivo de este prompt es que los PDFs que el sistema genera de verdad (al
aprobar una solicitud) se vean **igual que esas réplicas del HTML** — mismos
encabezados, mismas barras de sección con sus colores (azul institucional para
02/03/04/05, vino/maroon para 06/07), mismo orden de campos, y los datos reales de
la solicitud en el lugar correcto. Compara constantemente contra el HTML y contra
los PDF originales en `public/formatos/` mientras implementas.

### Detalles obligatorios por plantilla (ver HTML de referencia, secciones 3-7):

**Encabezado común a todas**: logo/sello IYEM a la izquierda + "INSTITUTO
YUCATECO DE EMPRENDEDORES" + "Dirección de Innovación y Competitividad
Empresarial", badge "CRÉDITOS IYEM" a la derecha, línea de programa, título del
documento centrado.

**Fila de modalidad** (checkboxes): marcar visualmente (☑ relleno en azul/vino)
SOLO la modalidad real de la solicitud (`modalidad.nombre`), dejar sin marcar las
demás. Para F-PR-OCC-01/06 (Artesanal) no hay fila de modalidad múltiple, va fijo
"MODALIDAD CREA ARTESANAL".

**Barras de sección** (`INFORMACIÓN DEL SOLICITANTE`, `DESTINO DEL CRÉDITO`,
etc.): fondo azul institucional `#2056a8` con texto blanco, o vino `#8b1538`
para los formatos de Declaración de Bienes del Aval — igual que en el HTML.

**Checkboxes binarios** (Sí/No, Propio/Rentado, H/M, Casado/Soltero, etc.):
marcar visualmente la opción correspondiente al valor guardado en BD; dejar la
otra vacía. Si el dato no existe (es null), dejar ambas casillas vacías, no
asumir un valor por default.

**Campos vacíos / no aplicables**: si un campo no tiene dato (ej. "Dependencia
si aplica" cuando el usuario no es empleado público), mostrar el campo vacío o
"—" / "N/A", igual que se ve en el HTML de referencia — NUNCA omitir el campo
ni el rótulo.

**Tablas repetibles** (proveedores, clientes, deudas, conceptos de destino del
crédito, créditos de gobierno, bienes y derechos del aval): iterar sobre la
colección real (`@foreach`). Si la colección está vacía, mostrar una fila con
"No aplica" o el texto correspondiente (como en el HTML), no dejar la tabla sin
filas.

**Formato de moneda**: todos los importes deben mostrarse como `$X,XXX.XX`
(separador de miles + 2 decimales), usando el mismo helper de formato de moneda
que ya se use en el resto del sistema (o `number_format($valor, 2)` si no existe
uno centralizado).

**Declaración final + firma**: incluir el párrafo de "Bajo formal protesta de
decir verdad..." (texto exacto de cada PDF original — tomarlo de
`public/formatos/.../*.pdf` para no alterar la redacción legal), con
`Fecha de Solicitud` (fecha real del envío/aprobación) y el campo
`Nombre y Firma` en blanco con la nota "(firma autógrafa al entregar impreso)"
— igual que en el HTML de referencia.

**Pie de página**: nota de aviso de privacidad + código de formato y número de
página ("F-PR-OCC-XX R00 · Página X de Y"), igual que el HTML de referencia.

## 3. LÓGICA CONDICIONAL DE GENERACIÓN

Al momento de generar el ZIP (disparado cuando `SolicitudCredito.estatus` cambia
a `Aprobada` — ver punto 4), aplica esta lógica exactamente como en la sección
"2. Mapeo" y el ejemplo de ZIP del HTML de referencia:

```
SIEMPRE se generan:
  - Solicitud (F-PR-OCC-01 si Artesanal, 02 si Física Emprendedores/Sustentable,
    03 si Moral Emprendedores/Sustentable)
  - Ficha Técnica (F-PR-OCC-04)
  - Estado de Ingresos y Egresos (F-PR-OCC-05):
      - 1 copia "Proyección" si solicitud.es_emprendimiento = true
      - 2 copias "Histórico" + "Proyección" si es_emprendimiento = false

CONDICIONAL según tipo_garantia:
  - Si tipo_garantia = 'aval' → generar también Declaración de Bienes
    (F-PR-OCC-06 si Artesanal, F-PR-OCC-07 si Emprendedores/Sustentable)
  - Si tipo_garantia = 'prendaria' o 'hipotecaria' → NO generar el formato de
    Declaración de Bienes (la info de garantía ya va dentro de la Solicitud,
    sección "Garantía Prendaria"/"Garantía Hipotecaria")
```

Nombrar los archivos dentro del ZIP de forma clara y consistente, ej.:
```
F-PR-OCC-02_Solicitud_Persona_Fisica.pdf
F-PR-OCC-04_Ficha_Tecnica.pdf
F-PR-OCC-05_Ingresos_Egresos_Historico.pdf   (si aplica)
F-PR-OCC-05_Ingresos_Egresos_Proyeccion.pdf
F-PR-OCC-07_Declaracion_Bienes_Aval.pdf      (si aplica)
```

## 4. FLUJO DE ESTATUS (ver sección 1 del HTML — pasos 5, 6 y 7)

Verifica/corrige que el flujo sea exactamente este (si ya está implementado de
otra forma por un prompt anterior, ajústalo a esto):

1. Ciudadano completa el formulario y presiona "Enviar solicitud" →
   `estatus = 'Enviada'` → pantalla/notificación: "Tu solicitud fue enviada
   correctamente. El equipo de CREA está revisando tu información..." — el ZIP
   **NO se genera todavía**
2. Operativo cambia el estatus a `En_Revision`, `Documentacion_Incompleta`,
   `Aprobada` o `Rechazada` desde el panel operativo (esto ya debe existir;
   si no, no es parte de este prompt — solo verificar que el trigger del punto
   3 esté conectado a ese cambio de estatus)
3. SOLO cuando `estatus` cambia a `Aprobada`: disparar (vía Observer del modelo
   `SolicitudCredito`, o en el método del controller operativo que hace el
   cambio) la generación de todos los PDFs aplicables + el ZIP, y notificar al
   ciudadano
4. El ciudadano ve entonces la pantalla descrita en el paso 7 del HTML:
   mensaje "¡Felicidades! Tu solicitud va a pasar a Comité.", botón "Descargar
   formatos (ZIP)", instrucciones de entrega física, y el mapa/dirección del
   IYEM (reutilizar el mismo embed de Google Maps ya implementado en la sección
   de Contacto de la landing)

## 5. ALMACENAMIENTO Y DESCARGA SEGURA DEL ZIP

- Generar el ZIP con `ZipArchive` (PHP nativo) o la librería ya usada en el
  proyecto, conteniendo los PDFs aplicables según el punto 3
- Guardar el ZIP en disco `local` (privado), NUNCA en `public` — mismo criterio
  de seguridad de prompts anteriores (los PDFs contienen datos personales
  sensibles: domicilios, RFC, bienes patrimoniales del aval)
- Ruta autenticada de descarga: `GET /mi-portal/solicitud/{solicitud}/formatos.zip`
  verificando que el `solicitud->user_id` coincida con el usuario autenticado
- Si se solicita regenerar (ej. el operativo corrige un dato y vuelve a
  aprobar), sobrescribir el ZIP anterior, no acumular versiones
